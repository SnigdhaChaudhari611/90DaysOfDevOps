# Day 44 - GitHub Actions: Secrets, Artifacts, Shell Scripts and Caching

## Goal

Learn how GitHub Actions can securely handle secrets, pass data through environment variables, share files between jobs, run shell scripts, and cache dependencies.

---

## Task 1: GitHub Actions Secrets

### What I learned

GitHub Actions secrets are used to store sensitive values such as passwords, tokens, API keys, and credentials.

Secrets are accessed with:

```yaml
${{ secrets.SECRET_NAME }}
```

The actual secret value should never be printed in workflow logs.

### Example

```yaml
name: Secret Demo

on:
  workflow_dispatch:

jobs:
  secret-demo:
    runs-on: ubuntu-latest

    steps:
      - name: Check secret
        env:
          MY_SECRET: ${{ secrets.MY_SECRET_MESSAGE }}
        run: |
          if [ -n "$MY_SECRET" ]; then
            echo "The secret is set: true"
          else
            echo "The secret is set: false"
          fi
```

### Important

If a secret is accidentally echoed directly, GitHub Actions attempts to mask the value in the logs. However, secrets should still never be printed intentionally.

### Where to create repository secrets

GitHub repository:

`Settings → Secrets and variables → Actions → New repository secret`

## Task 2: Passing Secrets Through Environment Variables

A secret can be passed to a step as an environment variable.

```yaml
- name: Use secret
  env:
    MY_SECRET: ${{ secrets.MY_SECRET_MESSAGE }}
  run: |
    echo "Secret is available: $([ -n "$MY_SECRET" ] && echo true || echo false)"
```

This keeps the secret out of the command itself.

### Docker credentials

For Docker workflows, credentials can also be stored as GitHub secrets:

```text
DOCKER_USERNAME
DOCKER_TOKEN
```

Example:

```yaml
- name: Docker login
  uses: docker/login-action@v3
  with:
    username: ${{ secrets.DOCKER_USERNAME }}
    password: ${{ secrets.DOCKER_TOKEN }}
```

Never hardcode Docker credentials in a workflow file.

## Task 3: Uploading Artifacts

Artifacts allow a workflow to save files produced during a job.

Typical use cases:

- Build output
- Test reports
- Logs
- Coverage reports
- Compiled applications
- Configuration generated during a workflow

### Upload artifact

```yaml
- name: Create file
  run: echo "GitHub Actions artifact demo" > output.txt

- name: Upload artifact
  uses: actions/upload-artifact@v4
  with:
    name: demo-file
    path: output.txt
```

The artifact can then be downloaded from the workflow run in the GitHub Actions tab.

### Key point

An artifact is different from a Git commit.

It is a file produced and stored by the workflow for later use or download.

## Task 4: Sharing an Artifact Between Jobs

Jobs run on separate runners, so files created in one job are not automatically available in another job.

Artifacts can be used to transfer files between jobs.

### Job 1

```yaml
build:
  runs-on: ubuntu-latest

  steps:
    - name: Create artifact
      run: echo "Generated by Job 1" > result.txt

    - name: Upload artifact
      uses: actions/upload-artifact@v4
      with:
        name: job-output
        path: result.txt
```

### Job 2

```yaml
test:
  needs: build
  runs-on: ubuntu-latest

  steps:
    - name: Download artifact
      uses: actions/download-artifact@v5
      with:
        name: job-output

    - name: Read artifact
      run: cat result.txt
```

### Important concept

```text
Job 1
  ↓
Create file
  ↓
Upload artifact
  ↓
GitHub Actions artifact storage
  ↓
Download artifact
  ↓
Job 2
```

### Real-world example

A build job can create an application package and upload it as an artifact.

A later deployment job can download that exact package and deploy it.

## Task 5: Running a Shell Script

A shell script from the DevOps practice work was copied into the GitHub Actions practice repository and executed through a workflow.

Example:

```yaml
- name: Make script executable
  run: chmod +x ./scripts/system_info.sh

- name: Run script
  run: ./scripts/system_info.sh
```

### Why `chmod +x`?

A shell script needs execute permission before it can be run directly as:

```bash
./scripts/system_info.sh
```

Without execute permission, the workflow can fail with:

```text
Permission denied
Error: Process completed with exit code 126
```

The permission can be fixed inside the workflow:

```bash
chmod +x ./scripts/system_info.sh
```

Then:

```bash
./scripts/system_info.sh
```

### Alternative

The script can also be executed through Bash without making it executable:

```bash
bash ./scripts/system_info.sh
```

### Important learning

GitHub Actions runners are fresh machines. File permissions and other environment details should not be assumed.

## Task 6: Dependency Caching

Caching helps workflows avoid downloading dependency data from scratch on every run.

For npm, a cache can be configured with:

```yaml
- name: Cache npm
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
```

Then dependencies can still be installed normally:

```yaml
- name: Install dependencies
  run: npm install
```

### What is being cached?

In this workflow, the npm cache directory:

```text
~/.npm
```

is cached.

This is not the same as caching `node_modules`.

The `npm install` command still runs, but cached package data can reduce the amount of downloading required.

### Cache key

```yaml
${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
```

The key includes:

- Operating system
- Node-related identifier
- Hash of `package-lock.json`

If the lock file changes, the hash changes and GitHub Actions can create a new cache.

### What I observed

The first workflow run created the cache.

Later runs showed:

```text
Cache hit for: Linux-node-
Cache restored successfully
```

The dependency cache was restored successfully before `npm install`.

The workflow completed successfully.

### Important

Caching does not mean the entire dependency installation step disappears.

The workflow still runs:

```bash
npm install
```

The cache mainly helps avoid downloading dependency data again.

# Key GitHub Actions Concepts From Day 44

## Secrets

Used for sensitive information.

```yaml
${{ secrets.MY_SECRET }}
```

Never hardcode credentials in workflow files.

---

## Environment Variables

Pass values into a shell step:

```yaml
env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
```

Use inside the shell:

```bash
echo "$API_TOKEN"
```

Do not intentionally print sensitive values.

---

## Artifacts

Used to store files generated by a workflow.

Upload:

```yaml
uses: actions/upload-artifact@v4
```

Download:

```yaml
uses: actions/download-artifact@v5
```

Useful for passing files between jobs.

---

## Shell Scripts

Run scripts with:

```bash
./script.sh
```

If executable permission is missing:

```bash
chmod +x ./script.sh
```

Or:

```bash
bash ./script.sh
```

---

## Cache

Used to reuse dependency data between workflow runs.

```yaml
uses: actions/cache@v4
```

A cache key determines which cache can be restored.

# Interview Revision

### 1. What is a GitHub Actions secret?

A secure repository-level value used to store sensitive information such as tokens, passwords, and API credentials.

### 2. Why should secrets not be hardcoded?

Because anyone with access to the workflow source may be able to see them. Secrets should be stored in GitHub's secret store.

### 3. What is an artifact?

A file or collection of files produced by a workflow and stored so they can be downloaded or used by later jobs.

### 4. Why are artifacts useful between jobs?

Each GitHub-hosted job normally runs on a separate runner. Artifacts provide a way to transfer generated files between jobs.

### 5. What does `chmod +x` do?

It adds execute permission to a file.

### 6. What does exit code 126 usually indicate?

The command was found but could not be executed, commonly because the file does not have execute permission.

### 7. What is the difference between an artifact and a cache?

**Artifact:**
Used to preserve or transfer workflow output such as builds, reports, and logs.

**Cache:**
Used to reuse data such as dependency caches to make future workflow runs faster.

### 8. Does npm caching mean `npm install` is skipped?

No. The install command still runs. Cached npm data can reduce downloading and make dependency installation faster.

### 9. Why can one job not directly access a file created by another job?

Jobs normally run on separate runner environments. Files are not automatically shared between them.

### 10. How can a file be transferred between jobs?

Upload it as an artifact in the first job and download it in the second job.

# Useful Commands

### Make a script executable

```bash
chmod +x script.sh
```

### Run executable script

```bash
./script.sh
```

### Run script with Bash

```bash
bash script.sh
```

### Check file permissions

```bash
ls -l script.sh
```

Example:

```text
-rwxr-xr-x
```

The `x` indicates execute permission.

# Day 44 Takeaways

- GitHub Actions secrets keep sensitive values out of workflow source code.
- Secrets can be passed safely to steps through environment variables.
- Artifacts preserve files generated during workflow execution.
- Artifacts can transfer files between separate jobs.
- Shell scripts may require execute permission on the runner.
- `chmod +x` can fix an executable permission issue.
- Caching can reduce repeated dependency downloads.
- Cache keys determine which cached data can be restored.
- Artifacts and caches solve different problems.
- GitHub-hosted jobs run on fresh runner environments, so files and permissions should not be assumed to persist.

## One-line interview summary

**Secrets protect sensitive values, artifacts store and transfer workflow outputs, shell scripts automate runner tasks, and caches reuse dependency data to speed up future workflow runs.**
